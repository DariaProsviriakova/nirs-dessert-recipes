# BM25-поиск рецептов

Модуль BM25 подключён к backend SweetMate. Он строит корпус десертов из d0rj/povarenok_recipes_detail, индексирует поля рецепта и разбирает текстовые ограничения. Поиск работает независимо от необязательного GigaChat.

Для приложения из корня репозитория выполни:

    npm ci
    npm run prepare:data

Команда загружает Parquet с Hugging Face, строит корпус и индекс. Файлы находятся в bm25/data/raw/ и bm25/data/generated/ и игнорируются Git. Каждый новый клон должен подготовить данные локально.

Для поиска из каталога bm25:

    cd bm25
    npm ci
    npm run search -- "шоколадный десерт до 30 минут" --limit 10

Benchmark-команды из каталога bm25:

    npm run benchmark:prepare
    npm run benchmark
    npm run tune

## Корпус

Источник: [Povarenok recipes detail на Hugging Face](https://huggingface.co/datasets/d0rj/povarenok_recipes_detail). Скрипт загружает оба Parquet-файла из train split; всего в исходном наборе 154 158 записей.

В корпус попали 28 768 кандидатов на десерты:

- рецепты из ветки «Десерты»;
- кексы из ветки «Выпечка»;
- пироги и тарты, отобранные по сладкой начинке;
- несколько явно сладких категорий.

Категории с пометками «несладкий» и «закусочный» исключаются. Это практическая эвристика для первой версии, а не ручная проверка каждого рецепта: при интеграции корпус стоит выборочно ревьюить и уточнять правила.

Корпус хранит ID и ссылку на исходный рецепт, название, категории, описание, ингредиенты, шаги, метки, вкусы, назначение, время приготовления, число порций, КБЖУ, URL изображения при наличии и внутреннюю причину попадания в выборку. Фотофайлы не скачиваются: интерфейс загружает разрешённые URL Povarenok, а при отсутствии ссылки показывает заглушку. Время больше 24 часов отмечается как аномальное и не участвует в ограничениях по времени. Неположительное, нецелое или явно неправдоподобное число порций не нормализуется как корректное.

### Заполненность важных полей

| Поле | Записей | Доля корпуса |
| --- | ---: | ---: |
| Время приготовления | 18 686 | 64,95% |
| КБЖУ на 100 г | 28 607 | 99,44% |
| КБЖУ на порцию | 15 684 | 54,52% |
| Ингредиенты | 28 766 | 99,99% |
| Шаги приготовления | 22 765 | 79,13% |

В поиске КБЖУ нормализовано в `nutrition.per100g`, `nutrition.wholeDish` и `nutrition.perServing`; у каждого набора поля `kcal`, `protein`, `fats`, `carbs`. Если выбранная база или значение отсутствует, рецепт не проходит соответствующий фильтр.

## Поиск и разбор запроса

Поиск — fielded BM25 с русской Snowball-стемматизацией, нормализацией `ё → е`, отдельными весами полей и бонусами за точное совпадение названия или псевдонима. Текущие веса выбраны по компромиссу между ранжированием точных названий и полнотой по тегам/ингредиентам. Баллы BM25 нужны для сортировки; их нельзя показывать пользователю как вероятность или уверенность.

```js
import { parseQuery } from './src/query.mjs';
import { searchRecipes } from './src/bm25.mjs';

const parsed = parseQuery('банан до 200 ккал на 100 г без сахара');
if (parsed.clarificationRequired) {
  // Попросить пользователя уточнить запрос.
} else {
  const results = searchRecipes(index, parsed.searchText, {
    ...parsed,
    limit: 10,
  });
}
```

Поддерживаются ограничения по времени, например `до 30 минут`, `не дольше часа`, а также по КБЖУ с указанной базой: `до 200 ккал на 100 г`, `белка не менее 3 г на порцию`. Если в запросе есть число и КБЖУ без указания базы (`на 100 г` или `на порцию`), `parseQuery` возвращает `clarificationRequired: "nutritionBasis"`; числовой фильтр не применяется. Одновременное указание обеих баз требует отдельного уточнения.

`parseQuery` также распознаёт отрицания вроде `без сахара` и `без выпечки`. Ограничения можно передавать напрямую через `options.filters`: `maxTimeMinutes`, `minTimeMinutes`, `minServings`, `maxServings`, `nutritionBasis` и границы `nutrition`. Незаполненное время/КБЖУ исключает рецепт из результата с соответствующим фильтром.

CLI выводит JSON с ID, ссылкой на источник, временем, порциями и КБЖУ:

```powershell
npm run search -- "банан до 200 ккал на 100 г" --limit 5
npm run search -- "десерт без сахара" --limit 5
```

## Benchmark

data/manual-benchmark-queries.json — источник ручной разметки. В нём 20 запросов на естественном русском: от общего «хочу блюдо из банана» до сочетаний ингредиентов, способов приготовления и ограничения времени. Для каждого запроса сохранены релевантные ID, проверенный пул кандидатов и краткое объяснение решения.

npm run benchmark:prepare объединяет ручные случаи с десятью отдельными field-derived проверками ингредиентов, тегов, времени, отрицаний и КБЖУ. В data/benchmark.json у каждого запроса есть labelSource; ручные оценки не смешиваются с автоматически полученными списками.

На корпусе из 28 768 рецептов текущие метрики такие:

| Часть benchmark | Запросы | Macro Recall@5 | MRR@10 | Hit rate@5 |
| --- | ---: | ---: | ---: | ---: |
| Ручные запросы | 20 | 63,9% | 0,858 | 90,0% |
| Автоматические проверки по полям | 10 | 7,1% | 0,889 | 88,9% |
| Всего | 30 | 46,3% | 0,868 | 89,7% |

Пилотные значения для предыдущих 16 случаев (Recall@5 — 44,2%, MRR@10 — 0,933) напрямую не сравнимы с новой ручной частью: у неё другие запросы и gold-наборы. Низкий Recall@5 на field-derived запросах ожидаем для широких списков вроде «все рецепты с бананом» и не должен трактоваться как качество человеческих запросов.

У ручных qrels указан relevanceScope:

- corpus-scan — релевантные рецепты найдены сканированием подходящих по смыслу записей корпуса и проверены вручную;
- reviewed-top-10 — вручную проверена первая десятка поиска; Recall считается только по этому пулу и не является полным recall корпуса;
- targeted-recipe — запрос проверяет нахождение конкретного названного рецепта, а не всех похожих блюд.

Поэтому это полезный ручной benchmark для следующей итерации, но пока не статистически репрезентативная оценка всей системы. Он уже выявляет конкретный промах: запрос «творожное печенье с бананом и овсянкой» имеет семь проверенных подходящих рецептов, но ни один не попадает в текущую первую десятку.

npm run tune теперь сравнивает веса в первую очередь на ручных запросах и отдельно показывает field-derived результаты. На текущем наборе вариант tag-balanced-plus получил Recall@5 67,2% и MRR@10 0,867 против 63,9% и 0,858 у текущих весов. Это кандидат для следующего эксперимента, а не достаточное основание менять веса до расширения и повторной проверки разметки.

## Файлы

- `src/bm25.mjs` — индексирование и ранжирование BM25 с фильтрами.
- `src/query.mjs` — разбор времени, КБЖУ и исключений из естественного текста.
- `src/text.mjs` — нормализация, токенизация и стемминг.
- `src/recipe-utils.mjs` — разбор времени, порций и КБЖУ исходного датасета.
- `scripts/download-dataset.mjs` — загрузка Parquet.
- `scripts/build-corpus.mjs` — фильтрация и нормализация корпуса.
- `scripts/build-index.mjs` — сборка сжатого индекса.
- `scripts/create-benchmark.mjs`, `scripts/benchmark.mjs`, `scripts/tune-weights.mjs` — разметка, измерение и сравнение весов.
- data/manual-aliases.json — псевдонимы, добавленные вручную.
- data/manual-benchmark-queries.json — естественные запросы и ручная разметка релевантности.

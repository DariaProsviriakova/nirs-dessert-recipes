# NIRS Dessert Recipes — данные и правила

## 1. Назначение документа

Здесь объяснён смысл полей и зафиксированы точные правила поиска, ответов, хранения, доступа и проверки качества. Пользовательские требования собраны в [03-requirements.md](03-requirements.md), видимые состояния интерфейса — в [04-interface-and-behavior.md](04-interface-and-behavior.md).

ID имеют формат `RULE-GROUP-NN` и не переиспользуются. Статус **Есть** означает соответствие текущему коду, **Частично** — частичное соответствие, **Нет** — правило ещё не реализовано.

## 2. Смысл данных

### 2.1. Рецепт

Основной каталог `recipeLibrary` находится в `sweetmate-frontend/src/App.tsx` и содержит семь записей.

| Поле | Значение в продукте | Использование и наличие |
| --- | --- | --- |
| `id` | Идентификатор рецепта | Ключ карточки, избранного и счётчика; есть |
| `title` | Название десерта | Карточка и распознавание точного запроса; есть |
| `description` | Краткое описание вкуса или состава | Карточка, полный рецепт и поиск; есть |
| `image` | Путь к изображению | Карточка; JPG хранится в `public/images`; есть |
| `time` | Время приготовления | Подпись карточки; есть, отдельно не проверяется |
| `difficulty` | Уровень сложности | Подпись и поле текстового поиска; есть |
| `tag` | Категория или свойство рецепта | Подпись и текстовый поиск; есть |
| `ingredients` | Состав с количеством | Полный рецепт и поиск; есть |
| `steps` | Упорядоченные шаги | Полный рецепт; есть |
| `requestCount` | Начальное число для сортировки | Популярные карточки и разрешение равенства в ранжировании; демонстрационное значение |
| `aliases` | Короткие альтернативные названия и распространённые формулировки рецепта | Помогают найти рецепт, если пользователь не знает или не вводит его основное название; влияют на ранжирование карточек, но сами по себе не открывают полный рецепт |
| `sourceName`, `sourceUrl`, `author`, `checkedAt` | Происхождение и дата проверки рецепта | В коде отсутствуют |
| `allergens`, `servings`, `nutrition` | Аллергены, число порций и пищевая ценность | В коде отсутствуют; источник значений не определён |

### 2.2. Запрос и контекст запроса

Сообщение пользователя хранит `id`, `role: 'user'` и `text`. Нормализованный текст создаётся внутри поиска и отдельно не сохраняется.

| Поле контекста | Значение | Состояние |
| --- | --- | --- |
| `queryId` | Идентификатор отправленного запроса | Отдельно отсутствует |
| `text` | Исходная строка пользователя | Есть в сообщении чата; отдельной записи поиска нет |
| `normalizedText` | Текст после нормализации для поиска | Вычисляется функцией, отдельно не хранится |
| `filters` | Выбранные категории, время или ограничения по ингредиентам | Фильтров в интерфейсе нет |
| `sourceRecipeIds` | ID рецептов, попавших в результат | Карточки хранятся в ответе; отдельного поля события нет |
| `submittedAt` | Время отправки запроса | Отдельно не сохраняется |
| `resultStatus` | Найдены рецепты, пустой результат или ошибка | Явное состояние результата не записывается |

Результат локального поиска содержит до трёх рецептов. Ответ ассистента хранит текст и карточки либо подробности одного рецепта. Текст ответа задан в коде и не создаётся моделью.

Запись события аналитики содержит `eventId`, `accountId` для вошедшего пользователя, `sessionId`, `queryId`, `submittedAt`, `resultStatus`, `resultRecipeIds` и `durationMs`. Полный текст запроса не передаётся в административную аналитику. Эта структура не реализована.

### 2.3. Учётная запись и роль

| Поле | Значение | Состояние |
| --- | --- | --- |
| `email` | Адрес из демо-формы; края обрезаются, регистр приводится к нижнему | Хранится в `localStorage` |
| `displayName` | Имя в профиле | Хранится локально |
| `password` | Демо-пароль | Хранится открытым текстом; небезопасно |
| `accountId` | Внутренний идентификатор учётной записи | Отдельно отсутствует |
| `role` | Уровень доступа `user` или `admin` | Отдельного поля нет; фиксированный email включает демо-экран на клиенте, настоящую роль назначает сервер |

Пользовательская регистрация не назначает роль администратора. Роль задаётся сервером и не считается достоверной, если она передана только клиентским кодом.

### 2.4. Чат и сессия

В прототипе чат содержит `id`, `title` и массив сообщений. Чаты и избранное хранятся в `localStorage` под ключом, связанным с нормализованным email.

| Понятие | Значение |
| --- | --- |
| Чат | Локальная переписка, сохраняемая при перезагрузке этого браузера |
| Сессия входа | Текущий демо-профиль, отмеченный локальным email; серверной сессии нет |
| Событие поиска | Отдельная запись об отправке запроса; в прототипе не создаётся |

## 6. Правила поиска

| ID | Правило | Статус |
| --- | --- | --- |
| RULE-SRCH-01 | Запрос обрезается по краям, переводится в нижний регистр, `ё` заменяется на `е`, пунктуация становится пробелами, повторные пробелы схлопываются. | Есть |
| RULE-SRCH-02 | Точное вхождение основного названия или alias даёт 40 баллов. За каждое слово запроса начисляется первое подходящее совпадение: 8 баллов за название, 6 за alias, 2 за описание, тег, сложность или ингредиенты. | Есть |
| RULE-SRCH-03 | Выбираются до трёх рецептов с наибольшим баллом; при равенстве выше ставится больший исходный `requestCount`. | Есть |
| RULE-SRCH-04 | Полный рецепт открывается по точному вхождению названия основного рецепта. Одного совпадения с alias недостаточно. | Есть |
| RULE-SRCH-05 | Если все баллы равны нулю, текущий код всё равно возвращает три записи с наибольшими исходными счётчиками. | Есть; известное ограничение |
| RULE-SRCH-06 | Поиск выполняется синхронно по `recipeLibrary` в клиентском коде; сетевого поискового запроса нет. | Есть |
| RULE-SRCH-07 | Поиск BM25/RAG возвращает рецепты из утверждённого корпуса; параметры ранжирования подтверждаются benchmark. | Нет |
| RULE-SRCH-08 | Балл ранжирования используется внутри поиска и не показывается пользователю как оценка уверенности. | Есть |
| RULE-SRCH-09 | Слова отрицания и ограничения («не хочу», «без», «кроме») обрабатываются как исключения, а не как положительное совпадение. | Нет; текущий поиск их не распознаёт |
| RULE-SRCH-10 | При нескольких точных названиях в запросе пользователь получает варианты для каждого либо уточнение выбора; порядок массива рецептов не должен определять ответ. | Нет; сейчас выбирается первое название в `recipeLibrary` |

Aliases нужны для поиска по синонимам и распространённым вариантам названия: например, `кексы` помогает найти маффины. Они получают меньше баллов за отдельное совпавшее слово (6), чем основное название (8), чтобы точное название оставалось приоритетнее. Точное вхождение всей строки alias получает бонус 40, как и точное вхождение названия. Это внутренние баллы сортировки, а не оценка качества или уверенности; пользователю они не показываются.

| ID | Правило | Статус |
| --- | --- | --- |
| RULE-ANS-01 | В прототипе текст ответа выбирается локальным кодом из заранее подготовленных данных; это не ответ LLM. | Есть |
| RULE-ANS-02 | LLM получает текст запроса и только рецепты, возвращённые поиском. | Нет |
| RULE-ANS-03 | Ответ не добавляет ингредиенты или шаги, которых нет в найденных записях; при нехватке данных указывает на это. | Нет |
| RULE-ANS-04 | Объяснение связывает найденный рецепт с совпавшими условиями запроса. | Нет |
| RULE-ANS-05 | Ответ не заявляет лечебный, диетический или аллерген-безопасный эффект без подтверждённых данных. | Нет |
| RULE-ANS-06 | Если LLM недоступна, найденные карточки остаются на экране, а интерфейс показывает понятную ошибку. | Нет |

## 8. Правила аналитики

| ID | Правило | Статус |
| --- | --- | --- |
| RULE-AN-01 | В прототипе учитывается точный запрос по основному рецепту; локальный счётчик увеличивается на единицу и сохраняется в браузере. | Есть |
| RULE-AN-02 | Общий запрос, alias, ингредиент, открытие рецепта и выбор популярной карточки не меняют счётчик. | Есть |
| RULE-AN-03 | В общей аналитике один принятый непустой запрос учитывается один раз независимо от результата поиска. | Нет |
| RULE-AN-04 | Пустой или не прошедший валидацию запрос, повторное открытие результата и переход по карточке не считаются поисковым событием. | Нет |
| RULE-AN-05 | Популярность рецепта считается по его ID в результатах поиска, а не по лайкам или начальным демонстрационным числам. | Нет |
| RULE-AN-06 | Административная аналитика показывает агрегаты и не позволяет перейти от показателя к тексту запроса или личному чату. | Нет |

Сейчас `sweetmate:requestCounts` содержит начальные значения в браузере и не является общей статистикой.

| Показатель | Значение в целевой аналитике |
| --- | --- |
| Всего запросов | Число принятых поисковых событий |
| Запросы по дням | Число событий, сгруппированных по `submittedAt` |
| Популярные рецепты | Число попаданий каждого `recipeId` в результаты поиска |

Эти показатели не собираются сервером. В демо-панели вместо них явно показано отсутствие общей статистики; локальные значения популярности выведены отдельно.

| RULE-QA-02 | В benchmark каждому запросу соответствуют ожидаемые релевантные ID рецептов. | Нет |
| RULE-QA-03 | Для ранжирования рассчитываются Recall@k и MRR; набор включает названия, aliases, ингредиенты, теги и запросы без совпадений. | Нет |
| RULE-QA-04 | При сравнении алгоритмов используется один корпус и один набор разметки. | Нет |
| RULE-QA-05 | Качество выдачи и достоверность рецептов оцениваются отдельно. | Нет |

## 15. Как читать

Сначала смотри статус правила, затем группу ID: `DATA` — поля рецепта; `ACC` — учётная запись; `SOURCE` — происхождение; `SRCH` — поиск; `ANS` — ответ; `AN` — аналитика; `SESSION` — история; `AUTH` — вход и роли; `ADM` — панель администратора; `UI` — интерфейс; `ERR` — ошибки; `QA` — качество.

Если описание текущего поведения расходится с кодом, проверь реализацию в `sweetmate-frontend/src/App.tsx` и `sweetmate-frontend/src/styles.css`. Таблица требований связывает правило с проверкой и сценарием.
